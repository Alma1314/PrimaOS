# 证据范围与结论规则

本页整理[白皮书§13](../../Prima%20OS.md)与[阶段跟踪维护规则](../../Prima%20OS%20实现阶段.md)。各类证据证明的对象不同，不存在“QEMU 通过即可升级为证明”的自动层级。

## 主张与工件对应

| 证据 | 可支持的结论 | 不能直接支持 |
|---|---|---|
| 规范/设计审查 | 状态、操作与错误出口已定义，文本缺口按审查范围处置 | 行为已经实现、真实隔离成立 |
| MODEL-TEST / host 测试 | 可执行模型或纯逻辑在输入集上满足断言 | 真实页表/TLB、并发硬件保证 |
| Lean 定理 | 对明确模型/前提的形式性质；需指出定理与建模范围 | 完整 Rust 内核细化、未建模对象性质 |
| REFINEMENT-DESIGN | 抽象投影与细化关系的设计、可执行模型实验 | REFINEMENT-PROOF 已完成 |
| QEMU / KERNEL-TRACE | 固定配置下真实执行路径和明确观测被见证 | 实机普遍正确性、覆盖全部交错 |
| COMPAT-TEST / Linux 同源差分 | 冻结输入/观察集合上的结果一致 | 全部 POSIX/Linux 兼容、未测试错误路径 |
| lint / build / 零 unsafe 扫描 | 构建和源码规则通过 | 没有逻辑缺陷或完整安全证明 |
| 阶段签署 | 在声明范围与退出规则下接受阶段证据 | 超出该阶段的功能或证明 |

Lean 当前的 CDT 良构保持性和森林性有独立定理，不能笼统写成“没有任何证明”；同时它不建模完整 KernelState。具体范围见[Lean 映照契约](../../lean/README.md)。

## 报告必须能回答

1. 测了什么版本、配置、输入与观察值？本次结果还是引用旧报告？
2. 实际执行了什么命令？退出码/日志和结论是否一致？
3. 成功、失败、超时、资源回收与权限负例各覆盖什么？
4. 相对前序报告修复了哪些条目？还有哪些未覆盖或 workarounds？
5. 这些结果影响哪个 profile 行或阶段条件？是否仍需独立评审？

失败实验应保留。修复报告链接发现报告，在限定主题上补强或取代旧结论；旧报告中的失败不应被改成 PASS。

## 当前状态与历史证据

[阶段跟踪](../../Prima%20OS%20实现阶段.md)维护当前状态；报告保留运行时刻的事实。M17b-2 的 fork/wait 不完整与 M17b-4 的 W6 通过可以同时为真，区别是实现版本与观测范围。W6 仍保留原生 SYS_FORK workaround，不能抹掉适配层续执行问题。

[阶段5 M21](../superpowers/reports/2026-10-23-stage5-m21-exit-review.md)记录了测试通过，但明确没有组织级签署。整理文档不代签、不发布 profile v2、不关闭 BLK-003。

## 统计与性能

测试数量、TCB 行数、容量水位和时延都是带版本的测量值。当前值应重新运行对应命令，并记录环境；历史值留在报告。性能记录至少带 QEMU/guest CPU/host CPU 和方法，不能把候选目标写成已测结果。
