# 阶段 7 范围裁决：双 personality、系统硬化与 AArch64 机制验证

## 1. 身份、来源与效力

本文记录作者在 2026-10-31 本次阶段 7 讨论中，对 16 个逐项问题给出的明确选择。作者先要求
“你提问，我回答，最后总结成文档”，随后逐项确认下表内容。这些回答构成本次范围确认来源。

上位来源是[白皮书阶段 7](../../../Prima%20OS.md#阶段-7--扩展与硬化)与
[D11–D16 前置裁决](2026-10-28-stage6-7-release-decisions.md)。本文承接 D16 的九条子轨，
将其从候选清单收敛为本次必交付范围，并细化 D11 的动态链接目标、D14 的 personality 组合
及 D15 的架构验收边界。D15 的 SMP 前状态分区要求继续有效。

**状态是“范围已确认，技术规格与量化门槛待冻结”。** 本文不分配 ABI、不改变当前原语语义，
不产生运行或证明证据，不启动阶段 7，不签署任何子轨。当前进度和退出勾选仍只查
[阶段跟踪](../../../Prima%20OS%20实现阶段.md)。阶段 6 尚未退出；其冻结白名单、静态链接边界、
失败记录与未完成项均保留。

## 3. 九条子轨的必交付范围

沿用 D16 的子轨身份和优先级。P0/P1/P2 表示既有排序，**P2 不再表示本轮可以省略**；
整体退出需要九轨分别满足其冻结条件。下表是范围及验收义务，具体输入和技术契约见第 8 节的冻结门。

| 子轨 | 优先级 | 必交付范围 | 退出时必须提供的观察 |
|---|---|---|---|
| 7-0 工程底座 | P0 | 可复现 CI、验收分组与资源控制、五项性能基准、发布制品身份 | `test/lint/tcb/docs check` 在 CI 通过；基准、环境和制品可复核；性能门槛已冻结并通过 |
| 7-A 多 personality | P0 | Linux 与 Prima 原生/POSIX 的独立 ABI 路径、语义状态、根与能力视图；显式共享服务 | 两条路径均运行真实白名单；未授权跨域访问被拒；共享服务经授权；单侧故障及额度耗尽后另一侧持续进展 |
| 7-B SMP | P0 | 状态所有权与分区、AP 启动、并发调度、IPI、TLB shootdown、锁顺序 | x86_64 的 2/4 vCPU 验收；并行 fork/exec、阻塞唤醒和共享资源压力无丢唤醒；TLB 一致性及扩展性证据 |
| 7-C 计量与配额 | P1 | 核心资源及 I/O 的归属、计量、准入、超限行为、转移与回收 | 单域分别耗尽每类额度；另一域保持进展；成功、失败、取消、销毁和恢复后的账目一致 |
| 7-D 选择性撤销 | P1 | 派生授权及相关会话、映射、DMA 和未决请求的完整收回 | 撤销完成后旧授权不能再访问；重启不复活旧授权；无关域不受影响；已提交操作按冻结协议结算 |
| 7-E 动态链接 | P2 | Linux 和 Prima 原生/POSIX 各自的动态装载、共享库及白名单 | Linux 未修改动态 ELF 运行；Prima 原生/POSIX 动态应用运行；两条路径各有正反例和可复核构建/制品身份 |
| 7-F 设备与持久化 | P2 | 用户态块设备与网络驱动、DMA/IOMMU 隔离、从盘启动及跨重启文件持久化 | 分别证明受限 DMA、网卡收发、磁盘启动、文件跨重启保存；非法 DMA 和设备访问被阻止 |
| 7-G 透明恢复与监督 | P2 | 范围内 LibOS、共享服务及驱动的检测、状态恢复、重新授权与端到端请求恢复 | 用户态崩溃后受影响应用继续执行；冻结请求不丢失、不重复产生副作用；无关域继续进展；配额与审计可对账 |
| 7-H AArch64 | P2（后期） | 在 AArch64 上细化同一 POSIR 契约；单核能力、内存、调度、IPC | 同一冻结观察语义下通过对应 `COMPAT-TEST`；架构差异、故障注入与未覆盖项有明确映照 |

两种 personality 是 Linux ABI 与 Prima 原生 ABI 上的 POSIX 路径，不代表增加 BSD/Windows 兼容。
原生 API 与 POSIX 层可以共用通用机制，但不得以共享可写兼容状态代替独立实例。
同一应用域可以没有或拥有多个 LibOS；继续遵守白皮书的“应用域与 LibOS 正交”模型，
不因本范围选择而引入内核可见的 Linux 域或 POSIX 域类型。

跨域拒绝应测试未授权操作及其确定错误，不把 D14 中一个 `EACCES` 例子扩展为所有失败均须
返回同一 errno。过期句柄、无权限、撤销和资源不足须由相应契约分别定义。

## 4. 平台与应用边界

| 平台 | 正式验收范围 |
|---|---|
| QEMU x86_64，2/4 vCPU | 两种 personality、动态链接、核心及 I/O 配额、完整撤销、受限透明恢复、设备隔离与持久化；保留单核回归入口 |
| QEMU AArch64，1 vCPU | 同一 POSIR 的能力隔离、内存、调度与 IPC 机制验证；不要求 x86_64 的完整应用、SMP 或设备功能对等 |

QEMU 版本、machine/CPU、内存、固件/启动方式、设备及 IOMMU 模型仍待冻结。
硬件机制允许不同，抽象观察差异必须登记；第二架构不能靠悄悄修改 POSIR 来制造通过。

应用采用有限、版本化白名单，不宣称通用 POSIX/Linux 兼容。白名单需覆盖动态命令行工具、
Shell 脚本、进程/线程及网络和持久化操作，两条路径可以使用不同程序。Linux 制品保持未修改，
Prima 原生/POSIX 程序按其 ABI 构建；程序、库、解释器、构建输入及哈希分别登记。
编译器自举或系统内源码构建不属于本次必交付范围。

本次不新增可信熵、ASLR 或抗利用结论；动态链接运行不自动改变
[D13 的公开确定 `AT_RANDOM` 边界](2026-10-28-stage6-7-release-decisions.md#d13无熵条件下的-at_random--canary-策略)。
若应用或新增安全主张需要改变该边界，另做明确裁决。

## 5. 透明恢复的精确定义与待设计部分

故障范围限用户态 LibOS、共享服务及驱动组件崩溃，内核与 QEMU 保持运行。应用继续执行是
验收观察，不能以结束旧应用并启动一个新应用代替。整机断电后的应用续执行不在本次范围；
7-F 的跨重启文件持久化是独立义务。

对冻结操作，恢复必须保持应用可观察结果与副作用一致：

1. 操作拥有可跨服务重启识别的请求身份；身份的生成、持久性及复用规则由协议冻结。
2. 覆盖受理前、受理后、执行前、产生副作用后、记录结果前后及回复丢失等故障窗口。
3. 恢复后能够判断操作状态、获得既有结果或安全完成操作，不能盲目重放非幂等副作用。
4. 本地服务与测试对端共同承担去重和结果查询；证明范围只覆盖冻结的端到端协议。
5. 对外部副作用既检查应用返回，也检查对端或存储的实际执行记录，不能只验证“没有崩溃”。

普通、不参与协议的外部服务不属于“不丢失、不重复”保证范围；不能在最终签署中把这类场景
静默当成已通过。崩溃组件列表、并发故障数、监督者故障、重复崩溃、恢复时限、状态保存方法、
日志/检查点及对端承诺仍须在技术规格中冻结。本范围不预先选择具体恢复实现。

透明恢复不允许恢复已撤销授权。崩溃与主动撤销同时发生时，须按冻结的提交点和撤销完成点
给出操作结局；管理器只能显式授予符合当前策略的新授权，旧句柄不能复活。

## 6. 资源隔离与撤销的约束

### 6.1 配额与审计容量

CPU、内存、Task、句柄、请求队列、审计预算、磁盘空间、I/O 请求和网络带宽均需定义所有者、
单位、共享资源计费、额度转移、准入/拒绝、调度公平性和回收规则。磁盘空间与 I/O 请求、
网络带宽是分别计量的维度，不能以一项计数代表全部 I/O 配额。

当前[审计耗尽控制器](../reports/2026-10-30-stage6-audit-fail-stop.md)在耗尽后全局停止。
这一历史行为继续是当前实现边界。本次选择要求后续设计保证单域压力不能耗尽全局审计容量：
例如域预算、全局保留与可信导出等需进入架构评审，具体方案尚未选择。不得通过丢弃必要审计
或解除现有停止标记来满足可用性测试。真正全局、不可恢复的审计故障处理也需与该局部隔离
设计明确区分；在后继契约落地前，不修改阶段 6 的 fail-stop 语义。

### 6.2 完整撤销

冻结撤销域及完成点时，至少分别处理派生能力/别名、Namespace 引用、服务会话、既有 CPU 映射、
DMA 映射/设备活动及排队或已交付请求。撤销完成必须意味着旧授权不能继续访问；在 SMP 上
还需提供跨核翻译与在途访问的相应证据。

这不是把所有效果隐含塞进 `cap_drop`：沿用
[原语规范的撤销边界](../../../COSIR%20原语规范.md#47-撤销边界)，为管理协议和必要机制分别评审。
已有实现的子树撤销和 Gate 授权丢失清理是可复用基线，不能当作本节全部范围已完成。

## 7. 形式化与性能验收

### 7.1 必须证明的关键性质

新增机制需有机器检查的关键性质证明，至少覆盖配额守恒、撤销后的授权失效、恢复协议的请求
去重及状态一致性。证明需列明状态、操作、假设和性质，并给出到生产实现的字段/操作映照及
已知缺口；相应 host、QEMU、变异或故障注入证据也要独立提供。

当前 Lean 覆盖边界以[Lean 映照契约](../../../lean/README.md)为准。现有句柄等切片的证明
不自动覆盖配额、DMA 或恢复状态机；本次没有新增证明。模型中的一般安全性、有限实现测试
和调度公平性/恢复时限主张分别举证，不将成功运行称为定理，也不将抽象证明称为完整内核证明。

### 7.2 先基线，后门槛

延续 7-0 的五项基准要求。讨论中提出的候选是原生 syscall、IPC 往返、Gate 往返、
页故障/COW、端到端 LibOS 操作；**这五个具体名称是待确认建议，不是作者已逐项冻结的清单**。

先冻结测试方法和环境，取得单核及 2/4 vCPU 的必要基线，再确认可接受开销、扩展性和回归
阈值。最终签署必须满足已冻结门槛；没有数值或只有“性能可解释”不足以关闭这一义务。
采样次数、分位数、吞吐、负载、宿主资源和参考侧口径需登记，QEMU TCG、KVM 与实机不能
混为同一组数据。此前计划的临时延迟目标不自动成为本阶段门槛。

## 9. 推进依赖与既有裁决关系

D16 的 `7-0 → 7-A → 7-B → 7-C/D → 7-G → 7-E/F → 7-H` 保留为起步排序假设，
本次没有另行确认完整施工顺序。新增范围带来以下需要在执行计划中表达的依赖：

- 7-A 的耗尽隔离验收需要最小配额与审计隔离先到位，不能等完整 7-C 结束后才定义。
- 7-B 先完成状态所有权和按 CPU 分区；共享对象、授权与计费的一致性不能靠复制状态绕过。
- 7-G 的协议设计可以先行，但覆盖动态应用、块设备和网络驱动的完整恢复验收依赖相应
  7-E/F 功能；不能把它读成“全部 7-G 在 E/F 开工前已完成”。
- 7-H 在拟复用的抽象观察语义稳定后推进，单核机制范围不被其它轨的应用功能自动扩大。

这些是依赖分析，具体工作包、资源安排和时程待执行计划确定，没有从回答中推导日历承诺。
九轨仍须分别签署；整体签署不能跳过必交付轨或代替子轨证据。

[原 D11–D16 裁决](2026-10-28-stage6-7-release-decisions.md)保留原文作为决策链：本文局部承接
其“范围未冻结/候选而非承诺”的阶段 7 描述，D11 的动态链接归属、D14 的研究优先和 D15 的
SMP 前状态分区仍有效。[旧执行计划](../plans/2026-10-27-stage6-7-refinement.md)中的估算、
较弱恢复范围与当时实现摘要不能视作本次范围的成本或完成状态。
