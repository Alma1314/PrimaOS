# S6-M1 递送机制的六项裁决（D17–D22）

承接 [S6-M1 递送设计提案](2026-10-29-stage6-m1-delivery-design.md)的六个开放问题，
编号接续[阶段 6–7 裁决](2026-10-28-stage6-7-release-decisions.md)的 D11–D16。

## 性质与效力

- 这是**机制范围裁决**：决定 ABI 号段、答复宽度、内存模型、`fork`/`exec` 立场、
  抽象模型路线与队列策略。不是实现，不产生运行证据，不勾选 S6-D2。
- 裁决只约束 S6-M1 的实现边界；不改阶段 6 退出条件措辞，不改 profile/SPEC-152。
- 每项都有重裁触发；与 D11–D16 一样，裁决不因"以后可能更好"而保持沉默。

## 裁决摘要

| ID | 裁决 | 一句话理由 |
|---|---|---|
| D17 | 批准**追加**号段 73–78，逐项在实现时分配；1–72 不重编号 | 用 IPC/信号接口拼装同步递送会把两种语义混在一起，更难审计 |
| D18 | v1 答复**只写 `rax`**；整帧答复另立机制，随 S6-M4 | 整帧答复等于让 LibOS 装载新上下文，需要新的帧校验与能力，风险与 S6-M1 无关 |
| D19 | v1 **内核代理复制**（≤4 KiB/次，只用记录下来的参数地址） | 复用既有 COW 正确的 copy 路径；映射授权要先有 7-D 撤销语义 |
| D20 | v1 门控任务的 `fork`/`exec` **由 LibOS 答复 `ENOSYS`**，行为留 S6-M4 | 进程身份与地址空间替换属于 Linux 语义，内核不该代替 LibOS 决定 |
| D21 | 抽象模型采**候选 A**（复用 `BlockedWait`＋请求对象） | 改动是加法；新增 `BlockedCall` 状态要同时改状态机、Lean 与 trace 断言 |
| D22 | 队列满时**阻塞**（可被信号打断），不丢弃、不返回 `EAGAIN` | 丢弃会让一个系统调用凭空消失，最难审计 |

## D17：ABI 号段 73–78

**裁决：批准追加，逐项分配。**

- 现有 1–72 已由 SPEC-152 冻结，`52` 保留；本裁决**不重编号、不复用**。
- 73–78 在实现时逐个写入 `prima-abi`：`SYS_GATE_ATTACH`(73)、`SYS_GATE_WAIT`(74)、
  `SYS_GATE_COPY_IN`(75)、`SYS_GATE_COPY_OUT`(76)、`SYS_GATE_REPLY`(77)、
  `SYS_GATE_ABORT`(78)。**未实现的号不预留**（沿用 D2"只登记实际实现"的口径）。
- 命名保持 OS 中立：`gate_*`；不得出现 `libos`/`linux`/`persona` 字样进入内核符号。
- `prima-abi` 仍是实验性接口（不是稳定外部 ABI），新增号随实现提交并登记
  `docs/superpowers/compat/` 台账。
- 不采用"用 `SYS_SEND`/`SYS_RECV` + `SYS_EXC_*` 拼装"的替代方案：那会把信号/异步通知
  与同步递送绑在同一组语义上，负例（重复答复、孤儿化）无法稳定表达。

**重裁触发**：若 M1b 实现时发现 6 个操作不足以表达（例如需要 `gate_detach` 显式解绑），
可追加 79+，但仍不得重编号 1–72。

## D18：答复宽度——v1 只写 `rax`

**裁决：`gate_reply(req, value)` 只写请求者的 `rax`，不改 `rip`/`rsp`/`rflags`/其它寄存器。**

依据：整帧答复等价于"让 LibOS 装载一个新的用户上下文"，需要新的用户帧校验
（现有 `kernel/src/exc.rs` 的 `SretFrame` 校验器面向内核帧，且有严格的 RFLAGS 掩码）、
目标地址合法性检查与独立能力。这些工作属于 **S6-M4**（进程/线程/信号语义：`exec`、
信号帧注入），不属于递送机制。

由此得到的可测试性质：被门控的 `syscall` 无论答复值是什么，返回点永远是 `syscall`
指令之后——不会出现"答复把控制流搬走"的隐式行为。

**重裁触发**：S6-M4 需要内核支持"LibOS 注入信号帧/模拟 `exec`"时，可新增
`gate_reply_frame`（独立号段、独立权利、整帧校验）；届时 D18 只放宽到"允许第二种答复"，
不改变 v1 语义。

## D19：内存模型——v1 内核代理复制

**裁决：`gate_copy_in`/`gate_copy_out` 由内核代理复制，单次 ≤ 4096 字节，且只能以
请求里**已记录**的参数值（`args[i]`）为基址 + 有界偏移。**

依据：

1. 既有 `copy_user_bytes`/`copy_out_user` 已经处理跨页、非映射与 COW（`copy_out_user`
   会走 `prepare_user_u32_write` 建 COW 私有页）。代理复制直接复用这些正确性，
   不需要新写一遍权页/COW 交互。
2. 跨任务映射授权需要"临时把请求者页映射进 LibOS"并**可靠撤销**——这正是 7-D
   选择性撤销的范围；在没有撤销语义前实现它，等于把阶段 7 的难点提前埋进阶段 6。
3. 代理复制下内核仍是唯一搬运者，请求者的授权面不扩大（I3/I6 可直接成立）。

**明确偏差**：细化计划 S6-M1 第 2 条写"LibOS 经 vspace 能力读写请求者内存"，
本裁决改为代理复制。已在设计文书的"兼容偏差"登记。

**重裁触发**：M1e 计量显示复制占往返时间 >20%，且 7-D 撤销语义已可用时，重开为
映射授权；否则保持复制。

## D20：门控任务的 `fork`/`exec`

**裁决：v1 不提供门控语义下的 `fork`/`exec`。** 陷阱照常递送给 LibOS，由 LibOS
决定答复；v1 的实现路径是 `gate_abort(req, ENOSYS)`，行为在 S6-M4 定义。

依据：

- `fork` 改变进程身份与能力继承（受控继承 A），`exec` 替换地址空间；两者都是
  "Linux 语义 + 内核机制"的交叉点，正是 S6-M4 的主题。
- 白名单的 6 个 applet 与 2 个探针在 v1 验证路径中都不 `fork`/`exec`（`true`/`echo`/
  `cat`/`ls`/`uname`/`sort` 单进程；P1/P2 不派生）。
- 禁止"静默降级"：门控任务 trap 里的 `fork`/`exec` 必须得到确定性 `ENOSYS` 并留审计，
  不得被内核顺手当作原生调用执行。

**重裁触发**：S6-M4 立项时重开；届时需要定义子进程的门控继承（当前取向：**不继承**，
由服务管理器显式挂接）。

## D21：抽象模型候选 A（复用 `BlockedWait` + 请求对象）

**裁决：POSIR/COSIR 采用候选 A。** 请求者在 trap 期间仍处于既有 `BlockedWait`
（等待对象＝请求），答复是"信号等待对象 + 写返回帧"的组合操作；门控本身是能力对象。

理由与条件：

- 现有状态集合 `Ready | Running | BlockedRecv | BlockedWait | Faulted` 已能表达
  "不在 CPU 上、等待他人唤醒、返回帧由他人决定"；新增 `BlockedCall` 会同时牵动
  §12.10 的 `exc_resume` 前提、`status = Faulted ⇔ pending_exc ≠ None` 一类不变量、
  Lean 细化与既有 trace 断言，成本与收益不对等。
- 采纳 A 的**前置条件**（不满足则退回 B）：
  1. COSIR 评审确认门控的五个事件
     (`GateAttached`/`Delivered`/`Replied`/`Aborted`/`Orphaned`) 足以重建审计链；
  2. 评审确认 A 没有把 Linux 语义偷偷带进抽象层（请求对象不携带调用号含义）；
  3. 请求对象的等待/唤醒复用 `wait_signal` 语义时，证明"答复一次性"由请求能力
     生命周期保证，而非由状态机外的约定保证。

**重裁触发**：上述条件任一不成立，退回候选 B（新增 `BlockedCall`），并且必须在 M1b
接线**之前**切换（接线后再换状态机会让 QEMU 见证与 trace 断言双重返工）。

## D22：队列满策略——阻塞，不丢弃

**裁决：门控队列满时，新的 trap 阻塞（可被信号打断），不丢弃、不返回 `EAGAIN`。**

依据：丢弃意味着请求者的系统调用**凭空消失**——它既没有返回码也没被审计为失败，
比阻塞更难解释。阻塞可以被打断（`EINTR`/`RESTART` 或任务终止），因此 I4（有界等待）
仍然成立。

配套：

- 每门控队列 8、未决请求总数 64、门控 16 个；全部在 `gate_attach` 时**预检**，
  不足返回 `ENOSPC` 且不改变既有状态。
- 必须有一条负例：队列满 + 请求者在阻塞中被信号打断 → 确定性 `EINTR`（或 `RESTART`
  重放产生新请求），不得留下已入队但无人服务的僵尸请求。
- 无内核超时（与设计文书的限制一致）：有界性来自 reply/abort/中断/终止四条路径，
  不来自计时器。

**重裁触发**：多客户端场景下出现队头阻塞使某个客户端饿死时，重开为"按客户端公平
轮转"或"每客户端一个门控"，而不是改成丢弃。
