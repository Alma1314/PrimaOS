# PrimaOS 异构 ISA 融合内核方案

本方案定义 x86_64 与 AArch64 在同一融合域中协同运行的内核结构：各 ISA 使用本地代码与
硬件上下文，共享一份通用对象、Capability 与资源权威状态，共同细化一个逻辑 POSIR 状态。
部署目标为同一发布镜像适配纯 x86_64、纯 AArch64 与满足准入条件的混合平台；单 ISA
运行是只有一种 ISA 参与的特例，三种配置遵守同一套对象语义。

状态为工作设计，尚未实现。共享 ABI、平台原子/一致性契约及实现映照必须在对应切片实施前
冻结；本文不发布机器 ABI，不改变[当前阶段](../../../Prima%20OS%20实现阶段.md)或退出勾选。
上位边界为[白皮书 §18.5](../../../Prima%20OS.md#185-异构-isa-融合内核)、
[原语规范](../../../COSIR%20原语规范.md)和[阶段 7 范围](2026-10-31-stage7-scope-decisions.md)。

## 1. 目标与范围

- 一个融合域对应一个逻辑内核状态和统一的对象/资源身份域。
- x86_64、AArch64 内核执行体按 ISA 构建，直接协调共享对象的生命周期。
- Capability 不可伪造、token 位置唯一、页帧唯一归属和失败原子性跨参与 ISA 成立。
- OS personality、guest ABI、文件/句柄/信号等兼容语义保持在用户态。
- 首个机制基线允许每个 ISA 一个 CPU；使用更多 CPU 须分别提供对应架构的 SMP 证据。

融合域要求成员内核共同受信，平台提供共享内存一致性、互操作原子操作和跨簇通知。
普通网络连通不构成融合域。内核成员之间不提供恶意隔离；用户态应用与 LibOS 仍受
Capability、页表和资源边界约束。首版不迁移运行中的内核栈或特权执行上下文。

## 2. 总体结构

```text
                  一个融合域 / 一个逻辑 POSIR 状态
        x86_64 内核执行体                 AArch64 内核执行体
        trap / CR3 / APIC                 trap / TTBR / GIC
        per-CPU 栈与就绪队列              per-CPU 栈与就绪队列
                    \                       /
             共享对象、Capability/CDT/位置、资源账本与审计
             共享 ABI + 跨 ISA 原子/锁 + 通知/失效/回收
                    /                       \
        用户态 personality/服务           用户态 personality/服务
                    \                       /
                 显式授权的应用共享内存与服务会话
```

共享内核区只允许内核执行体访问，与用户态共享 Segment 分开授权。内核共享区可在各 ISA
映射到不同 VA，对象引用经统一 ID 或相对偏移解析。应用地址空间的布局由其装载契约决定，
不能把用户态同 VA 要求直接套到内核共享区。

### 2.1 通用机制、架构后端与平台适配

| 层 | 内容 | 代码与状态边界 |
|---|---|---|
| 通用机制 | 对象/能力、Task 通用状态、等待、资源与审计事务 | `kernel` 中同源编译为各 ISA 原生代码，操作共享权威记录 |
| ISA 后端 | trap/syscall 入口、寄存器/FPU、页表编码、TLB 和本地中断 | `prima-ostd` 内按目标静态选择；上层仅编排经过约束的硬件接口 |
| 平台适配 | CPU/芯粒拓扑、启动、共享区、通知、时间转换与访问阻断 | 区分 ISA 与板级/封装级能力；按平台 profile 验证，不以 CPU 型号推断互连能力 |
| 用户态 | personality、服务、驱动策略和应用 | 按目标 ISA 装载，授权边界与现有分层一致 |

本机入口保存本地现场，将原生调用解码为通用请求，执行相同的授权/对象事务，再由本机
后端完成硬件动作和返回。Linux/Windows 号及结构转换仍由用户态 personality 完成。
共享事务遇到远端硬件动作时使用显式请求与确认，不在持锁期间等待另一 CPU。

优先演进现有 crate：拆分 `kernel::bootstrap` 的通用状态与本地状态，迁移入口全局槽，
在 `prima-ostd` 增加架构/平台模块，由 `xtask` 组织双构建与验收。共享布局先留在内核内部
模块，实际有独立使用者后再考虑提取 crate；不预建动态后端框架。

### 2.2 统一发布镜像与三种运行配置

统一镜像是包含多 ISA 原生代码、启动入口、系统组件和 manifest 的发布容器；各 CPU
执行匹配自己的机器码。镜像标识/哈希可相同，运行配置按实际平台选择。

| 平台 | 启动与运行 | 验收边界 |
|---|---|---|
| 纯 x86_64 | 启动 x86 执行体，建立一个仅含 x86 CPU 的融合域 | 原生执行；未使用的 ARM 载荷不参与运行 |
| 纯 AArch64 | 启动 ARM 执行体，建立一个仅含 ARM CPU 的融合域 | 原生执行；未使用的 x86 载荷不参与运行 |
| 混合平台 | 引导者建立共享状态，另一 ISA 执行体经加入协议参与 | 两侧操作同一权威对象，并分别通过入口、通知和失效验收 |

[UEFI 启动规范 §3.5.1.1](https://uefi.org/specs/UEFI/2.10_A/03_Boot_Manager.html#removable-media-boot-behavior)
允许同一介质包含 `BOOTX64.EFI` 和 `BOOTAA64.EFI`。这提供多架构启动入口的格式基础；
混合平台其余 CPU 的启动仍需平台协议，不能从两个 EFI 文件推出异构 CPU 自动上线。
BIOS、UEFI 与板级固件支持逐项登记；统一镜像不承诺任意机器或任意设备均可启动。

manifest 须绑定构建版本、载荷 ISA/特性、完整性信息、共享 ABI 版本、平台 profile 和
所需成员集合。固件/平台描述指定引导者及其余 CPU；缺失载荷、能力不符或加入失败时，
拒绝该配置。混合配置失败不得静默伪装成纯 ISA 成功；仅显式选择的单 ISA profile 可
在核实未加入 CPU 无法访问共享资源后启动。用户程序仍需匹配 ISA 的映像或另行验收的翻译层。

### 2.3 芯粒硬件基础与平台准入

封装内一致性芯粒是本设计的重要目标场景，以下标准与工艺提供分层基础；它们不是
Prima 已验证的平台组合，也不直接保证任意 x86/ARM 芯粒互通。

| 基础 | 提供的条件 | 本方案仍须固定的条件 |
|---|---|---|
| [FCSA 1.1.0](https://www.opencompute.org/wp-content/uploads/2026/10/FCSA-1.1.0.pdf) | ISA 中立的芯粒系统架构；§7.2.3 的一致性接口采用 CHI C2C，§7.2.9 描述 MSI/内存映射中断转发 | 具体拓扑、规则级别、启动/控制实现与混合 ISA 适配；其单一系统软件映像不等同于本文的统一磁盘镜像 |
| [CHI C2C Issue A](https://documentation-service.arm.com/static/691c2cfd69f16e048ca621a4) | 跨芯粒传输 CHI 事务，面向多芯片 SMP 与一致性加速器连接 | 端点/桥接器、原子与 DVM 能力、事务顺序和错误处理；能力表中原子/DVM 可不支持，必须核对双方 |
| [UCIe Streaming](https://www.uciexpress.org/post/ucie-1-1-provides-streaming-protocol-solution-for-error-detection-and-replay) | 为 CHI 等协议提供芯粒间传输；1.1 Streaming Flit 提供错误检测/重放支持 | 精确版本、封装/链路配置和协议映射；UCIe 接口本身不证明缓存或 CPU 原子互操作 |
| [先进封装](https://www.tsmc.com/english/dedicatedFoundry/technology/platform_HPC_tech_WLSI) | CoWoS、SoIC 等支持异构芯粒集成与高密度互连 | 电气、热/功耗、时钟、复位与制造实现；封装本身不提供对象一致性或锁语义 |

参考组合为 FCSA 系统组织、CHI C2C 一致性事务、UCIe 传输与相应封装。各 ISA 的
缓存/原子操作须经本地互连或桥接器正确进入同一一致性域；x86 接入尤其须有具体实现证据，
不能仅凭 FCSA 的 ISA 中立性或 UCIe 标识认定可接入。

平台 profile 至少包含共享范围与属性、物理资源映照、互操作原子宽度/对齐/顺序、通知与
确认、时间转换、复位/访问阻断，以及启动与故障边界。CXL 3.x 另提供跨主机一致性共享的
[标准基础](https://computeexpresslink.org/wp-content/uploads/2023/12/CXL_3.0_white-paper_FINAL-1.pdf)，
是否满足相同准入条件逐项验证。研究起点可复现 Stramash-QEMU；其宿主 TSO 和原子翻译
配置限制须保留，不能以模拟通过替代真实 ARM 弱内存顺序或目标芯粒的验证。

## 3. 状态所有权

| 状态 | 归属 | 保持条件 |
|---|---|---|
| 对象 ID、generation、Capability/CDT/位置、Namespace、通用等待 | 融合域共享权威，按对象/所有者分区 | ID 不冲突；token 至多一个位置；容器与位置双向一致 |
| Task 身份、状态、CPU owner、阻塞/唤醒票据 | 共享通用记录；现场由对应 ISA 解释 | 同一 Task 至多一个运行 owner；入队/唤醒与状态迁移一致 |
| Segment、抽象映射、物理资源身份与分配账本 | 融合域统一归属 | 共享物理页不被多个本地分配器重复分配；失败与回收守恒 |
| 审计预算、序号与提交记录 | 共享规则下分区计费、线性化提交 | 必要审计先预检；域内顺序明确；不靠丢审计保证进展 |
| 页表页、CR3/TTBR、TLB、入口栈、FPU/异常帧、APIC/GIC | ISA/CPU 本地 | 本地编码对应共享抽象映射；现场不被其它 CPU 覆盖 |
| per-CPU 就绪队列与热路径缓存 | CPU 本地 | 服从 Task owner/代次；缓存不能成为第二权威来源 |
| Linux fd、Windows handle、signal/TEB、翻译器代码缓存 | 用户态服务或执行进程 | 不进入内核共享对象模型，不混用不同应用的可写语义状态 |

分区遵守 D15 与[SMP 状态设计](2026-11-27-stage7-smp-state-partition.md)。融合通过共享
权威对象及其协议实现，不以一把覆盖全域的大锁代替状态分区。

## 4. 共享 ABI

共享布局须固定版本、端序、字段宽度、对齐、原子操作宽度与内存属性，并提供两种 ISA
构建产物的布局断言和兼容性校验。引用采用对象 ID/代次或共享区偏移；不得跨执行体直接
使用 Rust 默认布局、裸函数指针、vtable、本地栈指针或另一架构的硬件页表结构。

每类共享记录须定义拥有者、可变字段、锁域、访问规则、提交点及销毁条件。ABI 不匹配时
拒绝加入，不能靠解释部分字段继续运行。共享布局变更须先更新版本与映照，再更新访问代码。
特权寄存器、原子底层、通知与入口汇编归 `prima-ostd`；`kernel/src` 保持零 `unsafe`。

共享记录须有固定布局与显式填充检查，但 `repr(C)` 本身不证明并发访问安全。底层访问
封装须约束原子/非原子混用、别名、生命周期和缓存属性；锁、访问许可和代次也必须跨执行体
有效。不得让两份程序分别创建对同一可变记录的独占 Rust 引用，再以本地类型检查冒充全域
互斥证明。上层通过受限访问器、快照和守卫操作记录，布局与同步映照共同接受审查。

## 5. 一次引导与成员加入

1. 引导 leader 建立融合 epoch、平台资源清单、共享区和初始 Authority，仅初始化一次。
2. 各执行体初始化本地页表、入口栈、中断控制器、CPU 身份和异常现场。
3. 加入者核对 manifest、共享布局、平台原子/一致性 profile 与本地资源映照。
4. 完成对象访问、通知和失效握手后，才发布参与 CPU 并允许接收任务。
5. 加入失败时撤回预留资源；清理或隔离未完成前不得发布任务或复用共享资源。

加入者不得重复 bootstrap 同一资源或再次发放初始根。加入/退出/重新加入需要新的成员代次，
旧消息和旧票据不能作用于新成员；代次检查不替代对旧 CPU/DMA 访问的实际阻断。

## 6. 跨 ISA 同步与原子提交

缓存一致性、内存顺序和原子性分别定义、分别验收。共享 CAS/RMW 的宽度、对齐、内存属性、
acquire/release 与 fence 规则必须能在两种 ISA 间互操作；进程内 helper 锁不能代替另一
执行体也参与的共享锁。LL/SC 的实现与失效条件须有明确映照。

锁顺序采用任务/调度域 → 地址空间/页帧域 → 资源/审计域，并细化到实际对象表；跨 ISA
路径遵守同一顺序。持锁期间不得切任务、等待目标 CPU 确认或执行无界工作。
IRQ/NMI 入口不能递归获取被中断上下文持有的锁。

每个受保护操作在提交前完成身份、权限、参数、容量和审计预检；共享记录、token 位置与
容器更新在同一逻辑提交内生效。失败保持抽象状态不变。多执行体提交不得留下重复 Authority、
半发布 Task、部分撤销子树或已回收仍可访问的对象。

现有 `ISSUE-REVOKE-CONTAINER-001` 尚未修复；对象融合片在复用退休路径前须闭合
[Namespace/消息位置与失败原子性偏差](../reports/2026-11-27-architecture-isa-re-review.md#issue-revoke-container-001-的精确范围)。

## 7. 调度、阻塞与唤醒

Task 的 host ISA 与可执行映像必须匹配；把 Task 移入另一核簇队列不会自动转换代码或现场。
首片固定 CPU 放置，创建时给尚未运行的任务指定在线 CPU；fork/exec 及唤醒服从已冻结的
放置规则。运行中迁移和 work stealing 不作为首片机制。

Task 通用记录包含执行 ISA、允许 CPU 集合、owner/代次、状态、等待/唤醒票据，以及本地
现场标识；具体字段与布局待冻结。现场标识解析到对应 ISA 本地表，不包含另一侧可解引用的
栈指针或寄存器结构。就绪队列由所属 CPU 更新，远端通过有界待决票据请求唤醒。

发布就绪任务时同时提交 Task owner、状态和队列票据。跨簇唤醒通过共享状态发布加通知
完成，接收方校验代次；重复通知不得重复入队，通知到达与进入 idle 的竞争不得丢失唤醒。
返回用户态前必须完成本 CPU 的入口现场、内核栈、TLS/FPU 与页表切换。

本地抢占计数与全局期限时间分开。共享等待表只使用统一 epoch/单位的单调时间；各 ISA
时间源未完成转换和误差验证前，由统一时间所有者处理期限，禁止直接比较两侧本地 tick。

## 8. 映射、失效与回收

资源清单为每个物理资源建立唯一身份与分配所有者；共享内核页和页表页纳入保留帧账本，
应用页纳入 Segment 归属。本地物理地址与 NUMA home 是细化信息，不构成另一套所有权。
映射操作保留 Segment 与目标地址空间的双重授权检查。

跨 ISA 改变活动映射时，先更新共享映射代次并阻止冲突的新访问，再通知所有相关 CPU
执行各自架构的失效操作，收集带代次的确认。发送方不得持目标 handler 需要的锁等待。
CPU/DMA 访问未确认终止前，数据帧、页表帧及相关身份不得复用。

超时或确认丢失不能返回“撤销完成”；资源保持隔离并进入故障处理。COW、共享 root、
解除映射、权限收窄、对象销毁和成员退出必须服从同一失效/回收协议。

## 9. 故障与信任边界

用户进程或服务故障由受限会话、Task 生命周期和资源所有者处理，不隐含重放结果不明的
非幂等操作。服务透明恢复继续依赖独立的端到端协议，融合本身不提供去重保证。

成员内核故障可能遗留共享锁或半提交状态，首版对整个融合域 fail-stop；不允许其它成员
直接绕过锁继续修改共享状态。若失联成员尚可访问共享页，必须先阻断其访问，禁止把窗口
交给新应用或新成员。任一成员内核被攻破视为整个融合域的内核信任失效。

该故障边界不扩大阶段 7-G 的用户态组件恢复范围。旧能力不因重启或重新加入复活，主动
撤销与故障清理须按各自完成点结算。

## 10. 用户态与编译边界

系统组件按目标 ISA 同源构建；guest ABI 前端按应用 ISA 选择，而非按 host 构建选择。
融合内核不解释 Linux/Windows 调用号，也不负责将任意第三方指令翻译为另一 ISA。
原样二进制的 native/DBT 执行保持用户态兼容层职责，不能用融合共享状态代替其兼容验收。

### 10.1 现有项目的设计依据与取舍

下表用于说明机制来源与借鉴边界，不恢复并行旧方案或另设阶段排期。

| 项目 | 原设计 | Prima 的借鉴与限制 |
|---|---|---|
| [Stramash，ASPLOS 2025](https://ssrg.ece.vt.edu/papers/asplos25.pdf) | 各 ISA 原生内核实例尽量共享数据；每实例页表指向共同物理页，提供全局内存分配、跨 ISA 页表锁、环形缓冲与 IPI | 作为融合机制主要参考；原型仍保留部分复制/原内核路径，不能等同于全部状态合并。不迁入 Linux 对象语义，不外推性能 |
| [Popcorn Linux，EuroSys 2015](https://www.ssrg.ece.vt.edu/papers/eurosys15.pdf) | 复制内核，以消息协调任务/资源并用软件 DSM 支持共享地址空间，结合编译器提供迁移点 | 参考迁移与提交边界；本设计融合域内不复制完整权威表。该论文实测平台为 Xeon/Xeon Phi，不将其单独当作 x86/ARM 融合证据 |
| [Barrelfish，SOSP 2009](https://www.sigops.org/s/conferences/sosp/2009/papers/baumann-sosp09.pdf) | 每核 CPU driver 处理本地保护/调度/硬件，用户态 monitor 用消息和一致性协议协调复制状态 | 参考 CPU 本地职责、显式通知及能力管理；共享权威状态保留在 Prima 融合内核，不照搬其复制模型 |
| [Helios，SOSP 2009](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/helios.pdf) | 协调内核与卫星内核各管本地调度/内存，以消息访问服务；应用中间语言编译到目标 ISA，亲和性影响放置 | 参考服务放置和本地/远端消息边界；不要求 Prima 应用采用其语言，也不把服务卸载当作内核状态融合 |
| [UNIFICO，CC 2024](https://www.pure.ed.ac.uk/ws/portalfiles/portal/416254222/UNIFICO_MAVROGEORGIS_DOA23122023_AFV_CC_BY.pdf) | 编译器统一多 ISA 的 ABI、地址及栈布局，减少迁移状态转换；论文假设复制内核，OS 机制在范围外，评估为单线程 | 参考未来可重编译组件；不替代融合内核同步/调度，不据相同栈布局声称任意位置可迁移 |

论文中的 Single System Image 表达统一系统视图，不能据此认定已经实现 §2.2 的同一磁盘

另行锁定版本、许可证、修改与测试，不能用参考论文的 PASS 作为 Prima 证据。

涉及 UNIFICO 的实现须先锁定[作者工件](https://zenodo.org/records/10567311)、源码/依赖/
许可与哈希，验证与本仓库 Rust、musl、TLS/FP 和库调用边界的适配；已有论文不构成

## 11. 实施顺序与交付

| 切片 | 交付 | 开启下一步的条件 |
|---|---|---|
| 共享基座 | 两 ISA 本地启动、平台 profile、共享 ABI、唯一初始化/加入、资源清单与统一镜像接线 | 布局兼容、重复初始化拒绝、能力不符拒绝加入、用户无法访问内核共享区 |
| 对象融合 | 共享对象/Capability/CDT/位置、分区锁、审计预检与提交 | 两执行体操作同一权威对象；成功/失败保持位置与容器一致 |
| 执行融合 | Task owner、跨簇唤醒、统一期限、页表投影与失效/回收 | 并行任务无现场串扰、双重运行、丢唤醒或旧映射访问 |
| 集成验收 | 资源压力、成员故障停止、应用/服务接线与性能基线 | 原始反例闭合；联合模型/代码映照和机器证据齐备 |

平台、ABI 字段、原子 profile、通知与失效完成点在相应切片实施前冻结。x86 SMP、AArch64
单核机制和 AArch64 SMP 的证据分别记录；既有 x86 AP 上线不等于异构融合已实现。

### 11.1 实现基础与首个运行切片

现有基础是 COSIR 的平台无关宿主模型、内核/OSTD 边界、x86 单核机制及
[AP 上线/每 CPU GDT-TSS](../reports/2026-11-27-p5-3a-percpu-gdt-tss.md)；AP 仍停放且
IF=0，没有并行调度、IPI 或 TLB shootdown。当前构建目标、入口和页表代码仍以 x86 为主，
尚无 AArch64 内核后端、统一多 ISA 镜像或融合运行证据。

先固定实验平台的共享内存/原子/通知契约，补 AArch64 最小启动与异常/内存后端，并并行
验证共享记录和事务模型。首个融合运行切片用两 ISA 各一个 CPU 对同一权威 Capability
执行派生/移动/撤销及槽复用，验证全域位置唯一和失败状态相等，再引入用户任务、跨簇唤醒
与映射回收。该切片不以完整 x86/ARM SMP 为前提，但两侧入口隔离和并发安全仍须先满足；
不能直接让现有全局 syscall 暂存槽在并行用户任务中运行。

## 12. 验收与证明义务

| 性质 | 观察/反例 | 所需证据 |
|---|---|---|
| 统一部署 | 相同镜像标识分别启动纯 x86、纯 ARM 与混合配置；缺载荷、ABI/平台不符、重复引导与加入失败 | 三种配置分别记录机器见证；原生执行与 profile 一致，不静默退化；性能变化另行实测 |
| 全局权威唯一 | 并发分配 ID、派生/移动/撤销、消息与 Namespace 转移、槽复用 | W3/W4/CDT 联合模型、实现映照、双 ISA 机器负例 |
| 帧与映射安全 | 同页重复分配、COW 竞争、失效确认丢失、成员停止后帧复用 | W6/W7/W16 与回收模型；页表/TLB/设备访问证据 |
| 执行一致 | 同 Task 竞争入队、idle/唤醒交错、syscall 同时进入、嵌套异常 | 唯一 owner/通知状态机；两 ISA 实际并行及故障注入 |
| 失败原子性 | 预留失败、加入失败、审计不足、复制/校验失败 | 状态相等与守恒检查；不能以尽力回滚替代提交协议 |
| 故障停止 | 成员持共享锁时停止、超时、旧代次通知与迟到确认 | 全域停止与访问阻断证据；未确认前资源不复用 |
| 兼容与性能 | 按冻结 profile 的真实应用、单核与多核同负载基线 | 各 ISA/后端分别差分；允许事件偏序，不强求并发日志逐字节相同 |

联合抽象函数须把共享对象和所有 ISA 本地硬件状态映射到一个 POSIR 状态，说明线性化点、
内部步骤、失败语义与模型外事件。现有 Lean 单核/切片证明不自动覆盖该联合细化；若需要
新的独立抽象语义，按白皮书 H1 反例规则修订规范，不能预先宣称 POSIR v1 必然不变。

本方案当前无新增运行或证明证据。共享布局、参与 ISA/平台、锁/原子规则、故障范围、
工具链、应用 profile 或观察语义变化时重新审核；实现状态只由阶段跟踪及对应证据报告维护。
