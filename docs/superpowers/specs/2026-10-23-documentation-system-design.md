# 文档系统设计与维护契约

本规范约束文档组织、检索、元数据和维护，不改变 OS 语义、ABI 或阶段退出条件。初次验收见[报告](../reports/2026-10-23-documentation-restructure-report.md)，本次生命周期改造及删除清单见[2026-10-24 报告](../reports/2026-10-24-documentation-lifecycle-report.md)。本文原路径与 id 保留，2026-10-24 修订编写、检索与废弃规则。

## 1. 设计目标

文档必须支持大型项目中的三类操作：快速回答“现在是什么”；完整追溯“为什么、依据什么”；以有限上下文找到“改哪里、怎样验证”。人和 AI 使用同一份正文，生成目录只保存结构和引用，不复制整套事实。

验收标准：源文档全部可枚举；主题有契约/代码/证据入口；本地路径与 Markdown 锚点可检查；生成物可复现；状态与历史分离；失败和限制可追溯；无需外部服务即可检索。

## 2. 信息架构

| 层 | 工件 | 职责 |
|---|---|---|
| 项目入口 | 根 README、llms.md、docs/README | 项目定位和任务路由，不复制动态状态 |
| 当前状态 | 根实现阶段跟踪 | 阶段、勾选、阻塞与最新证据指针 |
| 权威契约 | 白皮书、原语规范、明确适用的切片规格 | 研究目标、抽象行为、局部设计 |
| 解释导航 | architecture、topics | 概念、源码归属、阅读链和操作手册 |
| 历史工件 | specs、plans、reports、compat | 预期、过程、实证及兼容范围分别存放 |
| 机器目录 | catalog.json、topics.json | 全量结构与人工精选阅读关系 |
| 可执行维护 | scripts/docs.py | 生成、离线检索、检查与自身自检 |

根权威文件与有效证据链保留；冗余或失效工件按 §9 登记后移除，不再要求永久保存所有执行草稿。新增说明放在 architecture/，设计/执行/证据分别放在 superpowers 对应目录；docs 根只放入口和机器目录。

## 3. 单一事实来源与权威冲突

进度问题由阶段跟踪裁决；抽象语义由原语规范裁决；研究与阶段定义由白皮书裁决；切片设计先确认批准与适用状态；实际行为由明确版本的代码/报告给出观察。

解释页不另建阶段状态表，不维护第二份 API 兼容矩阵。报告与台账可以包含带日期的观察；必须说明范围。若实现偏离规范，记录偏差并评审契约，不能因代码存在就反向定义语义。

后继报告只在明确范围内补强/取代前序结论。不得自动用“最新日期”判断批准、冻结、实现或证明状态。历史问题已修复时更新当前摘要，保留发现/失败报告。

## 4. 元数据与身份

新维护文档使用受限的扁平 YAML front matter，每行一个标量，不使用数组、嵌套或自动执行内容：

```yaml
---
id: topic-process
kind: topic
authority: explanatory
status: maintained
lifecycle: current
updated: 2026-10-24
---
```

- `id`：仓库内唯一、语义稳定；重命名需检查所有引用。历史未迁移文档以完整仓库相对路径为身份。
- `kind`：index、guide、reference、topic、specification、plan、report、template、agent-instructions 或 compatibility。
- `authority`：说明该文档回答哪类问题；explanatory/navigation 不覆盖契约。根权威角色由生成器显式登记。
- `status`：描述文档本身的维护/提案状态，不等于实现完成。模板使用 template；历史工件未补元数据时为 read-document-for-status。
- `lifecycle`：current / historical / deprecated；与 status 独立，含义和删除规则见 §9。新文档必须显式声明。
- `updated`：本次正文维护日期，不能伪造为实现/批准日期。日期文件名是工件日期线索，不是批准证据。

历史文件不强制补推断性的批准/完成状态。生命周期默认规则和人工例外登记在 §9；其值不代表批准或实现。标题、章节、编号提及和链接可自动提取，冻结/取代/签署关系必须由正文与人工阅读链说明。

## 5. 链接、章节与可寻址性

正文使用相对 Markdown 链接；含空格路径采用百分号编码。禁止新增仅 Obsidian 可识别的 wiki 链接。引用明确标题或章节，避免“见上面”成为唯一定位；章节应能独立理解其问题与范围。

标题可用中文，API/原语名保留精确英文。无需为了机器读取把全部正文翻译成英文；术语表和主题别名提供双语词汇。历史正文/代码样例中的原始路径不冒充有效链接。

`catalog.json` schema_version 2 记录生命周期、替代入口、删除记录，以及源文件 SHA-256、标题、行数、章节层级/起止行/锚点、原始链接和提及编号。源文档范围为根 Markdown、docs 下 Markdown、lean 根 Markdown；不索引 target、私有编辑器目录和依赖快照。生成的 catalog.md 不自索引，避免自哈希循环。

## 6. 主题包与关系

每个主题页回答：解决什么问题；哪些章节权威；如何读前序失败与后继整改；代码在哪；测试怎样观察；已知限制是什么。

`topics.json`包含唯一主题 id、title、aliases、guide、sources、code、tests。sources 表示相关阅读，不能当作“实现了”“证明了”或“取代了”的隐式有向关系。复杂关系在主题正文写明范围。

## 7. 检索与校验

`build`从源文档生成目录，输出稳定、无当前时间戳；同样输入必须生成同样字节。`search`实时检索正文和路径，默认排除 deprecated，保留 historical 以发现失败；可显式筛选生命周期。`inspect`返回文件的生命周期、替代入口、入站链接或删除恢复记录；`topic`返回精选路由。搜索排序只表示词法相关性。

`check`验证源文档唯一 ID、生命周期/恢复哈希/退役身份、主题引用、本地 Markdown 链接/锚点、残留 wiki 链接和生成物新鲜度。`check --base <提交>` 额外比较该提交与当前已保存文件（包含未跟踪文档），拒绝没有完整元数据的新文档、未登记的删除及恢复内容与基线不符。代码块与内联代码示例中的路径不当作活跃链接。远端链接不联网探测，技术结论、自然语言后继关系和批准真实性仍需审查。

解析器针对仓库使用的 Markdown 子集：ATX 标题、围栏代码、行内链接、链接定义和显式 HTML 锚点；不声称是完整 CommonMark/GFM 解释器。新增复杂语法时同步扩展验证并增加自检。

## 8. 编写与更新事务

先判断能否更新现有权威章节；同一事实不再新建摘要。跨文件、跨阶段或存在依赖的执行才单独建计划；简单改动可在报告写范围与命令。计划不复制实现清单，已完成后不继续维护“当前状态”。

新文档必须包含唯一 id、kind、authority、status、lifecycle、updated，并回答：读者要解决什么问题、适用版本/范围、上位来源、正文结论或预期、证据和限制、何时重审。规范、报告、计划、决策分别使用对应模板，复制后替换模板身份，禁止占位声明进入证据链。

一次行为变更按“契约 → 代码/测试 → 证据报告 → 台账/阶段 → 主题/目录”收口；如属纯文档修正，应明确“不新增运行证据”。规范/计划/报告目录 README 必须可发现新工件。

运行日志、完整命令输出及单独的日志／哈希附件不入库；原始输出留在 ignored `target/` 或 `/tmp/`。所属Markdown报告保留命令、基线／环境、退出状态、必要的关键输出与源码／输入哈希，失败和限制不能省略；不得将完整日志改扩展名塞进Markdown。历史日志附件清理须保留可验证的Git恢复版本、原路径／目录与承接报告；现有 `lifecycle.json` 的Markdown索引范围不变。

发布前运行 docs self-test、build、check，并记录仓库要求的测试/lint 结果。不能通过忽略全部历史链接、抹掉失败记录或自动勾选阶段条件来让校验通过。

## 9. 生命周期与废弃决策

生命周期只控制阅读和维护用途，不授予批准、不关闭 ISSUE、不签署阶段，也不表示内容全部正确。

| 值 | 用途 | 检索/维护规则 |
|---|---|---|
| current | 仍需维护的契约、手册、台账或活跃路线图；提案也可 current | 可作为该文档自身 authority 范围内的入口，仍须读 status 与正文 |
| historical | 带版本的过程/证据/候选设计 | 保留全文可搜；不从“历史”推断任务完成或证据失效 |
| deprecated | 已明确被取代、应停止照此实施，仍有追溯价值 | 保留原文与失败；必须登记原因、替代/纠偏入口；默认搜索排除 |
| removed | 已从工作树删除 | 只保存机器台账，不留占位正文；Git 可恢复 |
| unclassified | 旧材料没有显式生命周期 | 保留可搜，先读正文确认；禁止自动推断批准、废弃或完成 |

扁平 front matter 的 lifecycle 是维护文档的常用声明；旧文档例外与全部废弃/删除统一放在 [lifecycle.json](../../lifecycle.json)。同一路径两处声明必须一致；没有例外时，旧 plan/report 默认 historical，其他无声明材料为 unclassified。所有默认值只是文档用途，不是历史结论。台账 schema_version 1，每条包含 path/lifecycle/updated/reason/replacements；deprecated 必须保留来源和后继关系，不能仅凭文件日期、低引用数或测试数量判断废弃。

可删除：重复解释/旧交接、已由维护手册覆盖的一次性操作计划、明确放弃且没有独立决策或证据价值的草稿。只有部分内容过时，优先更新当前说明或登记 historical；仍被现行候选、阻塞或合同引用的设计不能因未实现就删除。

必须保留：当前契约与状态、冻结 profile、独立决策/采纳依据、唯一测试/证明/审查记录、失败与反例、发现→整改→复核链、阶段签署及其范围。后继 PASS 不是删除前序 FAIL 的理由。历史报告可以 historical；错误设计若仍需解释安全纠偏，可 deprecated 保留，而不是抹去。

## 10. 删除事务与可恢复性

1. 固定清理前提交，读取全文并检查入站 Markdown、主题、裸路径/文件名、阶段/台账引用。用 `inspect <仓库相对路径>` 查结构引用，辅以 rg 搜索裸路径。引用数不是删除许可。
2. 逐份记录删除理由与实际承接范围。选择 retained 的替代入口；没有功能替代时指向解释放弃原因、保留限制的报告。不得将旧失败链接偷换为成功报告来制造通过印象。
3. 台账登记 removed、原 id（无 front matter 时为旧相对路径）、完整 40 位 revision、原文 SHA-256、日期、原因和 replacements。revision 必须是可读取原文的本地 Git 提交；check 实际读取 Git blob 校验内容和身份。退役 id 保留，不可被新文档复用。
4. 删除正文，更新全部入站链接、目录 README、主题路由与当前入口；历史报告只改链接/删除注释，不改原实验结论。无需另建 archive 目录复制整套旧文档；外部旧路径通过台账查询恢复，不能保证外部链接仍直接打开正文。
5. 运行 self-test/build/check 和 `check --base <清理前提交>`；确认仅文档/工具变动，阶段勾选不变，报告记录删除清单、保留依据、实际结果及限制，同次提交。

恢复方法：`git show <revision>:<旧路径>`；迁移时旧路径保持 removed，新文件使用新 id；若需重新启用同一身份，明确撤销该退役记录并评审其全部引用，不能在台账仍标 removed 时重新创建文件。浅克隆缺少恢复提交时应补齐该历史再通过 check，不跳过恢复校验。

## 11. 复查触发与责任

修改某子系统的作者负责同次更新相关契约/证据/路由；维护者提交前检查范围、替代关系与删除理由。API/ABI、镜像格式、默认命令、上游快照或阶段证据变动，以及断链、重复摘要、发现“当前”与代码不符时，触发相关文档复查。无这些触发时不因年龄自动过期，不定期批量改日期，不把生命周期台账变成第二份实现状态表。
