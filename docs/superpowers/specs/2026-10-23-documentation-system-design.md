# 文档系统设计与维护契约

本规范约束文档组织、检索、元数据和维护，不改变 OS 语义、ABI 或阶段退出条件。实施记录见[计划](../plans/2026-10-23-documentation-restructure-plan.md)，验收见[报告](../reports/2026-10-23-documentation-restructure-report.md)。

## 1. 设计目标

文档必须支持大型项目中的三类操作：快速回答“现在是什么”；完整追溯“为什么、依据什么”；以有限上下文找到“改哪里、怎样验证”。人和 AI 使用同一份正文，生成目录只保存结构和引用，不复制整套事实。

验收标准：源文档全部可枚举；主题有契约/代码/证据入口；本地路径与 Markdown 锚点可检查；生成物可复现；状态与历史分离；失败和限制可追溯；无需外部服务即可检索。

## 2. 信息架构

| 层 | 工件 | 职责 |
|---|---|---|
| 项目入口 | 根 README、llms.md、docs/README | 项目定位和任务路由，不复制动态状态 |
| 当前状态 | 根实现阶段跟踪 | 阶段、勾选、阻塞与最新证据指针 |
| 权威契约 | 白皮书、原语规范、明确适用的切片规格 | 研究目标、抽象行为、局部设计 |
| 解释导航 | architecture、topics | 概念、源码归属、阅读链和操作手册 |
| 历史工件 | specs、plans、reports、compat | 预期、过程、实证及兼容范围分别存放 |
| 机器目录 | catalog.json、topics.json | 全量结构与人工精选阅读关系 |
| 可执行维护 | scripts/docs.py | 生成、离线检索、检查与自身自检 |

原有根权威文件和历史工件路径保留，避免破坏外部引用。新增说明放在 architecture/，设计/执行/证据分别放在 superpowers 对应目录；docs 根只放入口和机器目录。

## 3. 单一事实来源与权威冲突

进度问题由阶段跟踪裁决；抽象语义由原语规范裁决；研究与阶段定义由白皮书裁决；切片设计先确认批准与适用状态；实际行为由明确版本的代码/报告给出观察。

解释页不另建阶段状态表，不维护第二份 API 兼容矩阵。报告与台账可以包含带日期的观察；必须说明范围。若实现偏离规范，记录偏差并评审契约，不能因代码存在就反向定义语义。

后继报告只在明确范围内补强/取代前序结论。不得自动用“最新日期”判断批准、冻结、实现或证明状态。历史问题已修复时更新当前摘要，保留发现/失败报告。

## 4. 元数据与身份

新维护文档使用受限的扁平 YAML front matter，每行一个标量，不使用数组、嵌套或自动执行内容：

```yaml
---
id: topic-process
kind: topic
authority: explanatory
status: maintained
updated: 2026-10-23
---
```

- `id`：仓库内唯一、语义稳定；重命名需检查所有引用。历史未迁移文档以完整仓库相对路径为身份。
- `kind`：index、guide、reference、topic、specification、plan、report、template、agent-instructions 或 compatibility。
- `authority`：说明该文档回答哪类问题；explanatory/navigation 不覆盖契约。根权威角色由生成器显式登记。
- `status`：描述文档本身的维护/提案状态，不等于实现完成。模板使用 template；历史工件未补元数据时为 read-document-for-status。
- `updated`：本次正文维护日期，不能伪造为实现/批准日期。日期文件名是工件日期线索，不是批准证据。

历史文件不强制补推断性生命周期。标题、章节、编号提及和链接可自动提取，冻结/取代/签署关系必须由正文与人工阅读链说明。

## 5. 链接、章节与可寻址性

正文使用相对 Markdown 链接；含空格路径采用百分号编码。禁止新增仅 Obsidian 可识别的 wiki 链接。引用明确标题或章节，避免“见上面”成为唯一定位；章节应能独立理解其问题与范围。

标题可用中文，API/原语名保留精确英文。无需为了机器读取把全部正文翻译成英文；术语表和主题别名提供双语词汇。历史正文/代码样例中的原始路径不冒充有效链接。

`catalog.json`记录源文件 SHA-256、标题、行数、章节层级/起止行/锚点、原始链接和提及编号。源文档范围为根 Markdown、docs 下 Markdown、lean 根 Markdown；不索引 target、私有编辑器目录和依赖快照。生成的 catalog.md 不自索引，避免自哈希循环。

## 6. 主题包与关系

每个主题页回答：解决什么问题；哪些章节权威；如何读前序失败与后继整改；代码在哪；测试怎样观察；已知限制是什么。

`topics.json`包含唯一主题 id、title、aliases、guide、sources、code、tests。sources 表示相关阅读，不能当作“实现了”“证明了”或“取代了”的隐式有向关系。复杂关系在主题正文写明范围。

## 7. 检索与校验

`build`从源文档生成目录，输出稳定、无当前时间戳；同样输入必须生成同样字节。`search`实时检索正文和路径，限制结果数量与片段长度；`topic`返回精选路由。搜索排序只表示词法相关性。

`check`验证源文档唯一 ID、主题引用、本地 Markdown 链接/锚点、残留 wiki 链接和生成物新鲜度。代码块与内联代码示例中的路径不当作活跃链接。远端链接不联网探测，技术结论、自然语言后继关系和批准真实性仍需审查。

解析器针对仓库使用的 Markdown 子集：ATX 标题、围栏代码、行内链接、链接定义和显式 HTML 锚点；不声称是完整 CommonMark/GFM 解释器。新增复杂语法时同步扩展验证并增加自检。

## 8. 更新事务

一次行为变更按“契约 → 代码/测试 → 证据报告 → 台账/阶段 → 主题/目录”收口；如属纯文档修正，应明确“不新增运行证据”。规范/计划/报告目录 README 必须可发现新工件。

发布前运行 docs self-test、build、check，并记录仓库要求的测试/lint 结果。不能通过忽略全部历史链接、抹掉失败记录或自动勾选阶段条件来让校验通过。
