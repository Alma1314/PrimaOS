# DOC-008 / EXO-5：机制基线再评估（审查记录）

**日期**：2026-10-15
**状态**：审查结论，不改变 `Prima OS.md` / `COSIR 原语规范.md` 的 observable semantics；
后续若决定移动机制，必须先补用户态替代路径与等价证据。

## 方法

按 EXO-5 的四问评估当前机制：

1. 它保护哪类物理/逻辑资源？
2. 是否可用既有 `Capability + Segment + Send/Recv + Exception` 在用户态构造？
3. 移出内核是否破坏保护、原子性、终止性或可回收性？
4. 内核是否因此获得 OS personality 专属对象、名字或协议？

## 结论表

| 机制 | 归属判断 | 结论 |
|---|---|---|
| Capability | 权限/位置/派生树是不可伪造的授权机制，LibOS 无法在无内核支持下保证 token 唯一与权限单调 | **保留在机制层**；继续禁止服务名/服务协议进入 Capability 表 |
| MemorySegment | 页帧归属、映射权限、失败原子性与 TLB/页表保护必须受内核控制 | **保留在机制层**；`memseg_protect` 等由 COSIR 细化层承接 |
| Task | 执行、调度状态、地址空间根与异常入口必须由内核线性化 | **保留在机制层**；调度策略可继续留在用户态服务 |
| Send/Recv | 消息与 Capability 的原子移动、阻塞/唤醒与权限检查不可由普通用户态内存替代 | **保留在机制层**；协议、注册表、路由不进入内核 |
| Exception | 硬件事件不可伪造来源与硬件同步语义是保护机制 | **保留在机制层**；派生 kind 的策略留在 LibOS |
| Device | 端口/MMIO/IRQ/DMA 是物理资源，必须由 capability 授权 | **保留在机制层**；EXO-4A 已先补 Device 可见撤销；驱动协议留在用户态 |
| Namespace | 路径→Capability 是通用跨 personality 服务发现/授权机制，但“文件、目录、挂载策略”不应在内核 | **保留但收紧**：只保留通用路径/挂载/解析与环检测；文件语义、服务注册表、日志/存储策略明确在用户态 |
| Audit | 授权溯源依赖全局 Capability 派生/位置事件，用户态无法独立维护可信链 | **保留但收紧**：只记录授权/生存期事件；服务业务日志、witness 语义不进入内核 |
| Timer | 时间源/通知可能是硬件机制，但“谁在何时被通知”的大部分策略可由用户态定时服务表达 | **保留当前一次性通知，登记为可下移候选**；在用户态可保持 exactly-once/取消语义前不迁移 |
| WaitObject | 通用等待/唤醒可在一定程度上由 Send/Recv + Exception 组合，但原子等待条件与阻塞恢复仍是内核可验证边界 | **保留**；继续限制为通用对象，不引入 Mutex/Event/CompletionQueue 等 personality 语义 |
| 服务注册表 / 名称解析 | 完全属于用户态服务生态 | **移出**：EXO-2A 已先把服务名从内核映像目录移走；完整移出需 EXO-2 loader |
| 服务 witness / trace 解释 | 服务语义测试胶水，不是保护机制 | **移出**：EXO-3 目标；内核只提供通用 trace/调试通道 |

## 立即决策

- 不在此次评审中删除或修改任何 POSIR/COSIR 原语。
- Namespace/Audit/Timer/WaitObject 维持现状，但任何**新增**服务名、服务协议、业务日志字段
  进入这些机制，按 H1/H3 反例处理。
- Timer 与 Namespace 解析登记为“未来可下移候选”，前提是用户态替代品能保持相同原子性、
  终止性和失败原子性。
- EXO-2B/EXO-3 仍按用户态 loader / 通用 trace 方向推进；EXO-5 不阻塞它们。

## 边界

本审查只给出架构归属判断，不构成形式化证明，也不改变阶段 0–4 的退出条件。
