# P3-1：Store v2 会话

## 结论与范围

本报告记录 P3-1：把 P3-0 的纯状态机接成 Store 侧版本 2 会话——控制页 + 4 数据页
的多页段、doorbell 排空、公平配额、合并 COMPLETE、取消、重置、`EBUSY` 关闭与死亡
回收。**本片没有前端管线、没有 v2 wire 客户端、没有 v2 QEMU 证据**；v1 会话路径与
既有 72 轮事件保持。P3 未收口。

## 基线与输入

- 基线：`730957e`（P3-0 已提交）。
- 契约：[LibOS 数据通路契约](../specs/2026-11-10-libos-data-path.md) P3 节（草案，
  本片补写了 `generation_low8`、ACK 布局、CANCEL/CLOSE 折算 `tail` 与重置回收）。
- 计划：[P3 有界异步批量切片计划](../plans/2026-11-18-p3-async-slices.md) 的 P3-1。

## 关键设计决定

### wire 编码

- tag `0x5f30..0x5f35`：`ASYNC_OPEN/ACK/DOORBELL/COMPLETE/CANCEL/CLOSE`。
- `DOORBELL` 与 `CANCEL` 携带 `generation_low8<<40 | slot<<32`，`tail`/`ordinal`
  用低 32 位；Store 从控制页读取完整 `tail`，按 `head` 把 `ordinal_low32` 重建为
  完整序号（窗口 `K=4 < 2^32`）。低 8 位 generation 只是旧映像围栏，真正绑定仍是
  注册 cookie；该上限在“限制”中登记。
- 控制面回复统一 `ASYNC_ACK | slot<<8 | status`，status 为 0 或正 errno。

### 取消/关闭也读控制页

生产者总是先写页再发送，因此 CANCEL 与 CLOSE 也和 doorbell 一样先折算控制页
`tail`。否则“已发布但尚未发 doorbell”的批对 Store 不可见，取消只能得到 `Missing`，
关闭也可能越过未完成批。折算只调用 `Session::publish`，窗口/单调性语义不变。

### 公平排空

`async_batch::Store<N>` 每轮从上次游标起访问全部槽位，每个活会话至多认领
`FAIR_QUOTA=2` 个序号；服务在每轮后对推进过 `head` 的会话写回控制页并发一条合并
`ASYNC_COMPLETE`，轮次重复到没有任何会话推进。这样合并 doorbell 不会留下已发布却
无人唤醒的批，同时单个会话在一轮内不能越过配额。

### v2 数据页序号

数据页仍是 v1 编解码；新增 `bulk::validate_version_2` 只跳过 v1 的
`MAX_SEQUENCE` 上界，序号等于 `ordinal + 1` 的 u64 全值。v1 的 `validate` 与所有
既有调用逐字节不变。

### Store 栈预算

加入 v2 状态后，历史镜像里 Store 的 4 页用户栈不再容纳既有代理数据面调用链：
完整套件在 F1/V1/V3 出现 `kernel/src/cow.rs:314` panic（
`pick_next: fault requires a Ready successor`）。把 Store 的栈从 4 页提高到 8 页
（场景镜像既有 64 页不变）后同一套件转绿。`async_drain` 标记
`#[inline(never)]`，避免 4 KiB 页缓冲并入 `run` 帧。

## 实现内容

- `prima-runtime/src/bulk.rs`：新 tag、控制页常量、`initialize_async`/
  `validate_async`（magic `PBQ2`、version 2、`K`、保留位）、`validate_version_2`。
- `prima-runtime/src/async_batch.rs`：`Session::head`、`Store<N>` 轮转调度
  （`open`/`session_mut`/`remove`/`round`）；复用 P3-0 的 `Session` 状态机。
- `prima-runtime/src/protocol.rs`：`EBUSY=16`、`EALREADY=114`、`ESTALE=116`、
  `ECANCELED=125`。
- `prima-user/src/bulk.rs`：`execute_version_2`（与 `execute` 共用实现，仅换校验器）。
- `prima-user/src/service.rs`：`AsyncChannel`（5 页段、延迟销毁重试、按代理 index
  的 VA）、`async_request`（OPEN/DOORBELL/CANCEL/CLOSE）、`async_load`（控制页
  校验与窗口折算）、`async_drain`（FIFO 认领、取消写 `ECANCELED`、`EINVAL` 批级
  失败、合并 COMPLETE、写回 `head`）、死亡回收与代理关闭时强制回收。
- `prima-user/src/servicemgr.rs`：历史镜像 Store 栈 4→8 页。

## 失败、反例与限制

- **栈溢出失败保留**：第一次完整套件失败 5 项（default/F1/V1/V3 组的两次运行），
  统一 panic 于 `kernel/src/cow.rs:314`。仅把 Store 栈 4→8 页后 V3 与完整套件
  转绿；未加内核栈探针确认故障任务，因此“Store 栈溢出”是由单变量修复推断的
  强证据，不是直接观测。该容量调整只扩大栈，不放宽校验。
- **不是 v2 机器证据**：Store 的 v2 路径没有 wire 客户端调用；`async_request` 的
  页读取/回写/COMPLETE 发送只有静态检查。v2 的 QEMU 矩阵属于 P3-3。
- **取消已认领分支在实际 Store 中不可达**：单线程 Store 在一条消息内认领并完成，
  批次不会跨消息停在已认领态；`Cancel::Claimed` 与 `EALREADY` 只有状态机 host 证据。
- **generation 围栏只有低 8 位**：超过 255 次 OPEN/重置后低位可能重复；真正的
  隔离依赖注册 cookie 与段回收顺序。P3-2 若需要更强围栏必须改编码并重写契约。
- **重置后重新 OPEN 要求客户端先解除映射**：Store 保留段能力并返回 `EAGAIN`，
  这是 P2b-5 延迟销毁模式的沿用，不是泄漏。
- **批级失败写满 `MAX_OPS` 状态槽**：无效页（magic/保留位/序号）不执行任何 op，
  Store 无法得知客户端实际描述符数量，因此把 `EINVAL`（取消时 `ECANCELED`）写入
  全部 8 个完成槽；客户端只解释自己编码的描述符。
- 未做 `FAIR_QUOTA` 跨会话吞吐测量、SMP、恢复或性能门槛。
- 不改变 v1 会话、既有 72 轮事件、Linux 差分与 profile v1/v2；未新增 syscall。

## 阶段/profile 影响

不关闭 P3，不改变 P2 状态、阶段 7 九轨勾选或 7-A，不改变 D12 白名单与 profile。
契约 P3 节从草案向实现冻结推进了一步（补写了 v2 编码与重置回收），仍需 P3-2…P3-4
的机器证据。
