# Windows LibOS 计划书审计（2026-11-27）

## 1. 结论与范围

审计 [Windows LibOS 计划书](../plans/2026-10-31-windows-libos-roadmap.md) 与截至
2026-11-27 的 M0–M3 证据链。结论：**方向、边界与非主张质量高，没有发现把原型冒称
milestone 通过的情况**；但存在 3 项阻断级问题、6 项重大问题和若干次要缺口，主要集中在
“M0 未冻结却继续深入语义”“WIN-D3 用户 GS 与 SMP/内核上下文耦合”“D4 共享 root 多线程
无冻结设计”以及里程碑表与现有证据/阶段跟踪不同步。

本审计只读计划、规格、报告与阶段跟踪，不运行 Windows 程序、不审查实现代码的安全性质，
也不构成 M0–M10 任何里程碑的签署。发现按“阻断后续语义工作”“影响证据可信度”“文档与
可复现性”分级。

## 3. 阻断级发现

### B1 M0 未冻结，语义工作已推进到 M3

**证据**：M0 规格自述“不是 WIN-M0 的通过或签署”，WIN-D1–D7 全部未决；计划 §6 把 M0
列为 M1 依赖，但 M1–M3 已实现。所有报告均声明无 Windows 参考差分。

**风险**：错误值/`LastError`、路径大小写与共享打开、TEB/PEB 字段、API-set 路由等
语义尚无参考对象；M3 宿主模型只能证明“按当前假设解析正确”，不能证明 Windows 兼容。
若 M4 文件/句柄继续在没有 D1 的情况下冻结语义，返工范围会从解析层扩大到协议与验收。

**建议**：在计划中显式增加“原型通道”条款：M0 未通过前只允许 M1–M3 机制原型，报告必须
标注 `prototype`/未验收；冻结 D1（参考 Windows build、SDK/CRT、首批程序与导入闭包、
逐 API 行）之前，不得开始 M4 及之后的可观察语义实现。

### B2 WIN-D3 用户 GS 与 SMP/内核上下文耦合，计划未纳入跨轨决策

**证据**：计划 §2 与 §9 已把用户 GS 列为 D3，但按 Windows 单轨描述；
当前内核只有 FS TLS（`kernel/src/sched.rs` 的 `FS_BASES`），无 `swapgs`/用户 GS，
`kernel/src/msr.rs` 明示不做 per-CPU 区；S7-B.1/P5 的 CPU 本地状态故意未引入 GS，
P5-2 的 AP 也不装载每 CPU GDT/TSS/IDT。M2 的停车/发布已有 `task_create_held` 与
发布失败清理原型，**GS 部分没有任何机器证据**。

**风险**：Windows x64 的静态/动态 TLS 与 TEB 访问依赖用户 GS；同时 GS base 又是 x86_64
内核 per-CPU 状态的常见载体。先做 Windows 用户 GS 或先做 SMP per-CPU GS 都可能迫使
另一条轨道返工；`swapgs` 进入每个陷入路径还会影响审计与安全边界。

**建议**：把 D3 升格为 **SMP 与 Windows 联合架构裁决**，在 P5-3（每 CPU TSS/idle/
调度边界）与任何运行期 TEB/TLS 之前完成。至少比较：
(a) 内核 GS + `swapgs`（完整兼容，代价是陷入路径、每 CPU GS base 与安全评审）；
(b) 继续 FS/重映射（便宜，但不能宣称 Win32 TLS 兼容）；
(c) 推迟运行期 TLS、保持宿主模型（M3 永久部分）。
记录选择、代价与对 P5 分区的影响；不得由 Windows 单轨自行决定。

### B3 D4 共享 root / 多线程陷入没有冻结设计

**证据**：计划 §2 指出 `gate_client_root_is_exclusive` 拒绝共享地址空间客户端，§5.2
要求重新评审绑定身份、代次、COW 与请求寿命；M3 的 ring3 证据只有独立子任务（每任务
一个地址空间），没有同进程多线程、APC 或 WaitAll。

**风险**：M5/M6 的验收（多线程共享 TLS/句柄/地址空间、无线程错绑、APC）依赖 D4；
不冻结而先实现会复制 Linux 信号/等待的既有假设，之后难以证明不丢唤醒与线程归属。

**建议**：在 M5 前产出 D4 设计规格（线程身份、GS/TEB 切换、共享 root 的 Gate 绑定、
参数快照、取消/销毁与失败原子性），并给出反例矩阵；未冻结前 M5/M6 保持未启动。

## 4. 重大发现

### M1 里程碑表没有状态与证据列，原型与通过混淆

计划 §6 自述“以下全部是计划观察”，但 M1–M3 已执行，报告各自使用
`host-tests-pass-limits`/`implemented-with-limits` 等状态；计划表没有“当前证据/状态/
未满足项”列。例如 M2 表只剩“ring3 原样 PE64 调用替代导出、另一域继续”，而实际
M2 系列报告已改用真实 DLL 并登记了未覆盖项。

**建议**：增加里程碑证据矩阵（M0–M10 × 证据链接 × 状态 × 差距），并定义
“prototype pass ≠ milestone pass”；里程碑通过需要独立签署与退出项清单。

### M2 阶段跟踪的 Windows 段落已过时（本次已同步修正）

原文仍称“2026-11-26 起仅有 M0–M2 ring3……替代导入为手写桩，完整 M2 与 M0 均未通过”，
未反映 2026-11-27 的 M2 真实 DLL 与 M3 部分交付。**本审计同一提交已把该段改为当前
事实并链接新报告；这是纯状态同步，不改变阶段勾选。**

### M3 控制台优先与里程碑顺序冲突

作者选择“控制台与服务优先”，但控制台闭环在 M8，最晚；M0–M7 期间没有可观察的
stdout/控制台输出，Windows 参考差分要等到 M8 才能比较用户可见结果。当前 ring3 证据
只用共享结果页与退出码，没有 `WriteConsole`/stdout。

**建议**：增加 M2.5“最小控制台垂直切片”（stdout/stderr 写入 + 退出码 + 参数回显），
或把控制台输出并入 M2/M3 退出，使差分与自测更早可用；SCM 仍留 M8。

### M4 W^X 与按节权限：计划要求强于原型事实

计划 §5.1 要求“只读/可执行权限在发布前落实，不能靠永久 W+X”，但 M2/M3 的 ring3
原型把整映像（含 `.data`）按 R+X 映射；报告已声明，计划 M2 退出项没有登记该例外。

**建议**：在计划中增加“原型例外”清单，并把“按节权限 + 发布前无 W+X”明确为 M2 或 M3
的退出项；至少要求 `IMAGE_SCN_MEM_WRITE` 节在发布时不可执行。

### M5 “另一域继续运行”缺少对应证据

计划 M2 退出包含“另一域继续运行”；M2/M2 补片证据是父服务（同一域）继续存活，
没有 Linux/原生或第二 Windows 实例并存的观察。

**建议**：把该退出项改为“父任务继续”以匹配现有证据，或补一个双域并存的 QEMU 见证；
不得用单域父子存活替代。

### M6 API-set 与导入闭包仍缺 D1 清单

计划 §4 要求 API-set 路由与白名单；M3 的 `ModuleSet` 只按显式模块集合解析，报告说明
调用方须展开 `api-ms-win-*`，未实现名称猜测或清单。计划未把“API-set 清单”列为 D1 的
冻结物。

**建议**：在 D1 中冻结 API-set 映射表与首批导入闭包；计划中明确“禁止按同名文件猜测
API-set”，并把它作为 M3 的运行期退出前提。

## 5. 次要发现

- **m1 M0 的 holder 审计缺口**：计划 §2/§6 要求 M0 重新核对 holder、共享视图与地址
  空间身份；M0 规格只冻结 PE/ABI 输入，没有 holder 审计结论。建议在 M5 前补交。
- **m2 对抗性输入与资源上界**：解析器有溢出/边界检查，但计划没有恶意 PE 语料、最大
  节/导入/重定位/TLS 回调数量的上界，也没有 fuzz 或差分语料策略。建议加入 M1/M2 退出。
- **m3 夹具与工具链可复现性**：真实夹具由宿主 clang 22.1.4 + lld-link 18.1.3 生成，
  `build.rs` 依赖已安装工具而非锁定版本；报告哈希随环境变化。M0 应固定工具链与生成
  步骤，或在 CI 中记录可复核的生成/哈希。
- **m4 与阶段 7 的依赖映射**：M9 依赖配额/撤销/恢复（7-C/D/G），计划只在文字上提及；
  建议增加“Windows 里程碑 → 阶段 7 子轨证据”映射，防止硬化被提前宣称。
- **m5 签署主体与模板**：M0 冻结与 M10 签署的批准人、独立评审要求、报告模板未冻结；
  `WIN-M*` 编号与阶段的关系需要作者确认（保持候选 vs 进入阶段 8）。

## 6. 应予保留的优点

- 明确区分源码兼容、PE/Win32 导入兼容与 NT ABI，不夸大 v1。
- 强制真实 Windows 参考差分，明确 Wine 不能代签；没有参考就保持未完成。
- 禁止成功桩、永久 W+X、把任意句柄当 Capability；失败先记反例。
- 自有薄层优先，Wine 复用作为独立评审；不向内核加入 Windows 专属分派。
- 保留内核零 `unsafe` 边界与既有 Gate/内存/等待契约；停止条件可操作。
- M0–M3 报告均如实列出未覆盖项，没有把宿主模型或 ring3 原型写成 milestone 通过。

## 7. 建议的最小计划修订（未实施，待作者决定）

1. §6 增加“证据/状态/差距”列或独立矩阵；定义 prototype 与 milestone 通过。
2. 增加原型通道规则与报告标签，M0 冻结前不进入 M4+。
3. 把 WIN-D3 升格为 SMP/Windows 联合裁决，设定 P5-3 与运行期 TLS 前的期限。
4. 增加 M2.5 控制台垂直切片，或把 stdout/退出码并入 M2/M3 退出。
5. 增加“原型例外”清单，把按节权限/发布前无 W+X 列为退出项。
6. 修正 M2 的“另一域”措辞或补双域见证。
7. D1 增加 API-set 映射表与导入闭包；禁止名称猜测。
8. 增加恶意 PE 语料与资源上界；固定夹具工具链与哈希生成方式。
9. 增加 Windows 里程碑到 7-C/D/G 的依赖映射与签署主体。
